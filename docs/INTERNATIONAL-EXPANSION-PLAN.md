# PLAN — WORLDWIDE LEAD FINDER (245 countries)
### India first, every country covered, keyless engines only, Client + Master

**Status:** plan of record. Phases 0–3 are implemented; Phases 4–7 are the remaining work.
**Date:** 2026-11-14
**Companion docs:** `PLAN-BLAZING-SPEED.md` (measured speed work), `MASTER_SWEEP_INTELLIGENCE.md` (sweep semantics), `ORCHESTRATION-AND-RECOVERY.md` (queue/abort), `VENDOR_FIELD_MATRIX.md` (lead schema).
**Code anchors:** `server/src/services/sources/registry.js`, `server/src/services/localBrain/countries.js`, `server/src/services/omniSearchOrchestrator.js`, `client/src/v2/components/CountryFlagStrip.jsx`, `master/src/v2/components/CountryFlagStrip.jsx`.

## 0. The decision, in one screen

1. **India stays primary.** It is `COUNTRIES[0]`, keeps its own directory engines (JustDial, WeddingBazaar, WeddingWire, Mandap) and gets a larger flag plus a `HOME` badge in both dashboards.
2. **Every one of the 245 ISO countries is selectable and runnable.** Non-India countries run the keyless global bundle: OpenStreetMap, Google Maps, Google Local Finder, Web Discovery and official-website reading. Nothing needs an API key, an account or a credit card.
3. **Country context is threaded end-to-end.** Country code → Google `gl`, `Accept-Language`, phone country, currency, scope vocabulary (State/District/Mandal vs State/County/City), and the saved lead's `country` field. A search in Austin must never produce `+91` numbers or "India" as the state.
4. **Blocked sources stay blocked and visible.** YellowPages, Yell, BBB, IndiaMART and Google SERP are listed with an honest `blocked` status. We do not fake them, proxy around them or solve CAPTCHAs.
5. **"No rate limits" is not a promise we can make.** The limits are enforced by the destination websites. What we control is throughput: caching, deduplication, concurrency and several independent keyless sources. This is stated in the UI and in §9.
6. **Speed is a scheduling problem, not a "more requests" problem.** One browser budget, two-pass coverage (named localities first, grid last), zone context pooling, HTTP caching and O(1) dedupe. Targets in §6.

## 1. Coverage model

### 1.1 Country data

| Layer | File | Content |
|---|---|---|
| Curated profiles (16 markets) | `server/src/services/localBrain/countries.js` | Aliases, currency, phone code, admin vocabulary, regions/states |
| Generated ISO list (245) | `server/src/services/localBrain/worldCountries.js` | Code, name, currency, phone code, flag emoji |
| UI flag data | `client/src/v2/data/countries.js`, `master/src/v2/data/countries.js` | Same list, generated by `scripts/tools/gen-world-countries.cjs` |
| Detection | `detectCountry(text)` | Curated aliases → city aliases → generated names → `null` |

Rules:

- India is always `COUNTRIES[0]` and the default when detection returns nothing.
- `UK` normalises to `GB`; unknown two-letter codes are rejected, never guessed.
- Diacritics are stripped before matching (`São Paulo` → `sao paulo`).
- City aliases cover the major world cities so a bare city name resolves without a country word.

### 1.2 Country bundles

```js
INDIA_ENGINES = [openstreetmap, maps, google-local-finder, web-discovery, web-contact,
                 justdial, weddingbazaar, weddingwire, mandap]        // 9
INTERNATIONAL_ENGINES = [openstreetmap, maps, google-local-finder,
                         web-discovery, web-contact]                  // 5
```

`enginesForCountry(code)` returns the bundle filtered by access status, so a `blocked` or `untested` source can never leak into a run. India-only engines are hard-excluded for every other country.

### 1.3 What "coverage" means per country

| Level | Meaning | Countries |
|---|---|---|
| **Full** | Curated profile + all 5 global engines + admin regions | 16 curated markets (IN, US, GB, CA, AU, NZ, AE, SA, SG, MY, ZA, IE, DE, BR, JP, NG) |
| **Standard** | All 5 global engines, generated country/flag/phone data | The other 229 ISO countries |
| **Blocked (listed)** | A local directory exists but refuses automation | US, CA, GB, AU, NZ, AE, SA, SG, MY, ZA, IE, IN (IndiaMART) |

No country is "unsupported". The difference is how many extra local directories exist, not whether a search runs.

## 3. Country context — the contract

Every run carries a context object. Nothing downstream may hardcode India.

| Field | Source | Used by |
|---|---|---|
| `countryCode` | `detectCountry(location, cityHint, district, state)` → fallback `IN` | All engines, phone parser, lead store |
| `gl` | `countryCode.toLowerCase()` | Google Maps URL, Local Finder URL, HTTP Local Finder |
| `Accept-Language` | `en-IN…` for IN, `en-US…` elsewhere | HTTP tier |
| `defaultCountry` | `countryCode` | `normalizePhone`, `extractPhones`, `fastWebsiteExtract` |
| `currency` | `COUNTRIES[code].currency` | Dashboard, exports |
| Admin vocabulary | `topTerm`, `secondTerm`, `localTerm` | Scope picker (State/District/Mandal vs State/County/City) |
| `country` on the lead | `countryCode` | Stored vendor, CSV export, dedupe |

- [x] `fastGoogleHttp.js` derives `gl` and `Accept-Language` from the query.
- [x] `engine-google-serp-local.js` derives `countryCode`, passes `gl`, and parses phones with the country.
- [x] `engine-google-places.js` derives `countryCode` from `location`/`cityHint`/`district`/`state`, adds `?hl=en&gl=…` to the Maps URL, parses card phones with the country, and builds WhatsApp links from validated digits.
- [x] `fastWebsiteExtractor.js` accepts `{ defaultCountry, allowInternational }`; international `tel:` and `wa.me` links are parsed properly.

## 4. Mobiles and emails

### 4.1 Phone extraction

| Source | India | Everywhere else |
|---|---|---|
| Maps card text | Strict regex: `+91`, `0` trunk, 10-digit mobile `[6-9]…`, STD landlines | `extractPhones(text, { defaultCountry })` |
| `tel:` links | `normalizePhone` with `IN` | `normalizePhone` with country, `allowInternational: true` |
| `wa.me` links | Validated digits | Validated digits (no `91` prefix assumed) |
| Website text | Strict Indian regex | `extractPhones` + libphonenumber validation |
| Feed/detail panel | `normalizePhone` with country | Same |

Output contract per number: `e164`, `national`, `digits`, `displayPhone`, `callUrl`, `isMobile`, `isLandline`, `phoneType`. WhatsApp links are generated **only** for validated mobiles and use `phone.digits`, never a hardcoded prefix.

### 4.2 Email extraction

- `mailto:` links, visible text, JSON-LD and meta tags.
- Blacklist filters (wixpress, sentry, schema.org, example.com, CDN hosts, placeholder addresses).
- Home page + `/contact`, `/about`, `/impressum`, `/kontakt` variants fetched in parallel.
- One crawl per website per run, cached by URL.

### 4.3 Business details

Name, address, locality, district/state, postal code, country, coords, category, rating, reviews, hours, website, logo/photo, socials, contact person, VAT/GSTIN where present. Field rules live in `VENDOR_FIELD_MATRIX.md`.

## 5. Maps and location intelligence

### 5.1 What must not glitch

| Symptom | Cause | Fix |
|---|---|---|
| Same 20 places for every zone | No viewport bias | Zone `@lat,lng,zoom` in the Maps URL |
| Leads from the wrong city | No boundary check | `zoneDistanceReject` + bounding box + containment guard |
| "India" on a Berlin lead | Hardcoded fallback | Country-aware `state` |
| `+91` on a US lead | Hardcoded phone prefix | Validated `digits` |
| Empty map pins | Missing coords | Parse `!3d…!4d…` from the maps link; reverse geocode fills gaps |
| Duplicate pins | No spatial dedupe | O(1) RAM index keyed by phone/mapsLink/name+city |

### 5.2 Location intelligence

- Forward geocode: Nominatim → Photon (keyless), cached.
- Reverse geocode: fills village/mandal/district/state only when the lead has coords.
- Zone generation: named localities first, street grid last (see `PLAN-BLAZING-SPEED.md`).
- Country context never changes mid-run; it is resolved once from the user's location text.

### 5.3 Map UI

- Client and Master use the same map component and the same marker schema.
- Pins are clustered above 200 markers; clustering is client-side, no extra network.
- Country selection changes the map centre and the default zoom, and re-renders the flag strip.

## 6. Speed

### 6.1 Mechanisms (already in the codebase)

| Mechanism | Effect |
|---|---|
| Zone context pool | Reuses Chromium contexts; avoids 0.4–5.5 s cold-start per zone |
| One browser budget | Discovery and enrichment share slots; stops ~10 pages on 8 cores |
| Two-pass coverage | Named localities deliver ~97% of leads in ~35 s; grid is background |
| HTTP cache | Repeat queries answered from memory |
| O(1) dedupe | No DB scan per lead |
| Parallel page batches | Local Finder pages fetched together |
| Streaming inserts | Leads appear while the run continues |
| Media/font/tracker abort | Each page load is cheaper |

### 6.2 Targets

| Scenario | Target |
|---|---|
| First lead | < 3 s |
| 25 leads (dense city) | < 30 s |
| Full named-locality pass | ~35 s |
| Grid long tail | Background, cancellable |
| Repeat identical query | Near-instant (cache) |

### 6.3 What we will not do

- No CAPTCHA solving, no proxy rotation to defeat blocks, no forged sessions.
- No unbounded retry storms against a 429/403 — the ban guard backs off and reports it.
- No claim that a blocked directory "works".

## 9. Rate limits — the honest policy

The user asked for "aggressive, no rate limits". Here is the truthful position:

1. **The limits belong to the websites.** Google, JustDial, YellowPages and friends decide how many requests they accept. No client-side setting can remove that.
2. **Bypassing them is out of scope.** CAPTCHA solving, residential proxy rotation and forged sessions violate terms and break the "no extras" rule.
3. **What we do instead:**
   - Cache identical queries and pages.
   - Deduplicate before fetching.
   - Run independent keyless sources in parallel so one site's limit does not stall the run.
   - Respect `robots.txt` and crawl delays for HTML sources.
   - Back off and report when a site says 429/403 — then continue with the other engines.
4. **What the UI says:** "Running sources" and "Blocked sources" are separate counts. We never print "unlimited".

This is the maximum legal throughput. It is genuinely fast because the work is parallel and cached, not because limits are ignored.

## 12. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Google changes DOM | Selector fallbacks + card-text parsing + OSM as an independent source |
| A directory starts blocking | It is already `blocked` in the registry; nothing breaks |
| Wrong country detected | Curated aliases first, fallback to India, user can change the flag |
| Phone parsed with wrong country | libphonenumber validates; `allowInternational` only outside India |
| Slow long tail | Grid pass is background and cancellable |
| Duplicate leads | O(1) index on phone, maps link and name+city |
| User expects "unlimited" | Explicit wording in the UI and in §9 |
